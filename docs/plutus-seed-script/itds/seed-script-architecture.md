| ITD 1 - "Use a Python seed script with psycopg2 and environment-variable-driven configuration for Supabase connection." |  |
| :---- | :---- |
| **THE PROBLEM** | The seed script must connect to a Supabase PostgreSQL database, create the schema, load 10,000 transactions from `transactions.json`, seed the rewards catalogue and default user, and do all of this in a single command. It must be safe to re-run during development and support both local PostgreSQL and Supabase-hosted Postgres. The connection method, environment management, and re-run strategy all need clear decisions before writing the script. | **OPTIONS CONSIDERED (Decision in bold)** |
| **Option 1** | **Single Python script (`seed.py`) using `psycopg2`** — reads `transactions.json`, creates schema via inline SQL, inserts all rows with `execute_values()` for bulk insert, computes coin balance, and inserts rewards. Runs via `python seed.py` with a `DATABASE_URL` environment variable. |
| **Option 2** | Split into two scripts: `schema.py` (creates tables) + `seed.py` (loads data). Run both via `make seed` or a shell script. Separates concerns but adds complexity. |
| **Option 3** | Single SQL file (`seed.sql`) loaded via `psql $DATABASE_URL -f seed.sql`. No Python dependency. But SQL can't easily parse JSON, normalize timestamps in 3 formats, or compute coin balances. |
| **Option 4** | Python script using SQLAlchemy Core for DB operations. More ORM-like, but overkill for a seed script. Adds a heavy dependency. |
| **Option 5** | Node.js script using `pg` library. Works, but diverges from the Python backend choice. | **REASONING** |
| **Script approach** | Option 1 (single script) is optimal: it handles JSON parsing, timestamp normalization (3 formats), status normalization, coin calculation, and database operations in one coherent flow. The assignment's backend is Python (FastAPI), so `psycopg2` is a natural dependency — it's already in the backend's `requirements.txt`. A single command (`python seed.py`) is the cleanest for the README and reviewer experience. |
| **Connection management** | The script reads `DATABASE_URL` from the environment (via `os.getenv`). A `.env.example` file documents required variables (`DATABASE_URL`). `python-dotenv` can optionally load `.env` for local dev, but the script should also work with directly-set env vars (for Supabase deployment). This satisfies "one documented command." |
| **Re-run strategy** | `DROP TABLE IF EXISTS` for all tables at the top of the script, then `CREATE TABLE + INSERT`. This makes the script idempotent — running it twice produces the same state. Alternatives (`TRUNCATE` or `INSERT OR REPLACE`) are more error-prone with foreign keys and don't reset serial counters. |
| **Option 2 (split scripts)** | Separation of concerns is nice but adds friction: two commands to run, two files to maintain, and the schema must be in sync between them. For a 24-hour assignment, a single script is lower-risk. |
| **Option 3 (pure SQL)** | `psql -f seed.sql` is elegant but SQL cannot handle JSON parsing, multi-format timestamp normalization, or coin calculation logic. Would require pre-processing the JSON outside SQL, defeating the "single command" goal. |
| **Option 4 (SQLAlchemy)** | SQLAlchemy Core handles upserts and bulk inserts well, but adds a heavy dependency and learning curve. For a seed script with straightforward INSERTs, raw `psycopg2` is simpler and more transparent. | **TRADEOFFS** |
| | The single-script approach couples schema creation with data loading, meaning schema changes require re-running the entire seed. For a 24-hour assignment, this is acceptable — `DROP TABLE IF EXISTS + CREATE + INSERT` is fast for 10k rows. The `psycopg2` dependency must also be in the backend's `requirements.txt`. | **NOTES** |
| | - Bulk insert: use `psycopg2.extras.execute_values()` for inserting all 10k transactions in one batch (1–2 seconds). <br>- Idempotency: `DROP TABLE IF EXISTS` at script start means re-runs are clean. <br>- Dependencies: `psycopg2-binary` (or `psycopg2` with system lib) + optionally `python-dotenv`. <br>- Command: `python seed.py` (after setting `DATABASE_URL`). <br>- Local dev: can use Docker PostgreSQL (e.g., `docker run --rm -e POSTGRES_PASSWORD=pass -p 5432:5432 postgres:16`). |
