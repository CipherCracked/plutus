| ITD 1 - "Normalize timestamps to UTC, unify status casing, and skip duplicate transaction IDs during seed." |  |
| :---- | :---- |
| **THE PROBLEM** | The `transactions.json` dataset contains three data quality issues that must be resolved before insertion into the PostgreSQL `transactions` table: (1) timestamps are in **four** different formats (ISO 8601 datetime strings, Unix epoch milliseconds, date-only strings, and slash-separated DD/MM/YYYY HH:MM:SS strings), (2) the `status` field has inconsistent casing (`"SUCCESS"` and `"success"` are both present), and (3) there are 40 duplicate transaction IDs out of 10,000 records. The seed script must handle all three without data loss or errors. | **OPTIONS CONSIDERED (Decision in bold)** |
| **Option 1** | **Handle normalization in Python within the seed script** — parse timestamps with a multi-format try/except, normalize status with `.upper()`, and track seen IDs in a set to skip duplicates. Log warnings for skipped records. |
| **Option 2** | Use PostgreSQL's own parsing (e.g., `to_timestamp()` with type coercion) — insert raw values and let the database normalize. |
| **Option 3** | Pre-process the JSON with `jq` or a separate transform script, then load the cleaned data via `psql` or the seed script. | **REASONING** |
| **Timestamp normalization** | The three formats (`"2025-10-03T21:03:27Z"`, `1768265109000`, `"2025-07-03"`) require multi-format parsing. Python's `datetime.fromisoformat()` handles ISO strings, `datetime.fromtimestamp(ts/1000)` handles epoch millis, and `datetime.strptime(d, "%Y-%m-%d")` handles date-only. A try/except chain in the seed script is the most transparent approach. PostgreSQL's type coercion can't distinguish between a date-only string and an ISO datetime string without explicit casting, and epoch milliseconds would need explicit conversion — making Option 2 impractical for mixed formats. |
| **Status normalization** | A simple `.upper()` call on the status string resolves `"success"` → `"SUCCESS"` with zero cost. This is trivially handled in Python. PostgreSQL could do `UPPER(status)` on insert, but doing it in the seed script keeps the logic visible and testable. |
| **Duplicate IDs** | Tracking seen IDs in a Python `set` during iteration lets the seed script skip duplicates with a warning. This is transparent and logs exactly which IDs were skipped. PostgreSQL's `ON CONFLICT DO NOTHING` would also handle this at the DB level, but it silently ignores without logging, and requires the `id` column to be a primary key (which it is). |
| **Option 2 (PostgreSQL normalization)** | Would require inserting raw values into a staging table, then running SQL UPDATE statements to normalize. This is more complex, requires an extra staging step, and doesn't leverage Python's superior date parsing flexibility. |
| **Option 3 (pre-processing)** | Adding a `jq` transform step creates a two-step pipeline, violating the "single command" requirement. A separate Python transform script is just moving the same logic into another file. | **TRADEOFFS** |
| | Handling normalization in Python adds ~50 lines of code to the seed script, but keeps all data cleaning logic visible, testable, and debuggable. The `execute_values()` bulk insert still loads all rows in one batch — the per-row normalization happens during the pre-processing loop before insertion. | **NOTES** |
| | - Timestamp conversion logic: try `datetime.fromisoformat()` for ISO strings, `datetime.fromtimestamp(ts/1000)` for epoch ms, `datetime.strptime(d, "%Y-%m-%d")` for date-only, and `datetime.strptime(d, "%d/%m/%Y %H:%M:%S")` for slash format, all with UTC timezone normalization. <br>- Status normalization: `.upper()` on every status value. <br>- Duplicate handling: a `seen_ids = set()` tracks IDs; duplicates are skipped with a `print(f"WARNING: duplicate ID {id}, skipping")`. <br>- After normalization, all 10,000 rows (minus duplicates) are inserted via `psycopg2.extras.execute_values()` in a single transaction. |
