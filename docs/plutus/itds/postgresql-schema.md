| ITD 1 - "Use a flat transactions table with typed columns and a coins balance table for the Plutus schema." |  |
| :---- | :---- |
| **THE PROBLEM** | The application must serve 10,000 transactions with rich filtering (category, date, amount, payment status, merchant search) and sorting (date, amount) behind a transactions table, while also tracking per-user coin balances and redemptions for the rewards system. A single JSON dump or denormalized blob would be easy to seed but perform poorly on queries, lack proper indexing, and fail the assignment's "design an actual schema rather than dumping the JSON into a single column" requirement. | **OPTIONS CONSIDERED (Decision in bold)** |
| **Option 1** | **Flat transactions table** — each JSON field becomes a typed column (date, amount, category, merchant, payment_status, etc.). A separate `coins_balance` table tracks the running total. Seed loads JSON directly via INSERT. Fast to seed, all columns indexed. |
| **Option 2** | Fully normalized schema with foreign keys between `transactions`, `categories`, `merchants`, `users`, `coins_ledger`, `rewards_catalogue`, and `redemptions`. Enforces data integrity but requires multi-table seed (categories first, then merchants, then transactions with FK refs) and ledger-based balance computation. |
| **Option 3** | Minimal approach — flat `transactions` table + a single `user_coins` balance table. No audit log for redemptions, no FK relationships. Simplest possible schema. | **REASONING** |
| **Option 1** | Satisfies "actual schema, not JSON dump" by mapping each JSON field to a typed column. Seed script is trivial (one INSERT per JSON record). All filter dimensions are column values with direct indexes. The flat structure means no joins — queries are fast and predictable. The only downside is merchant and category names are repeated across rows rather than normalized, but for a 10k-row fixed dataset that doesn't change, this is negligible (≈200KB of duplicated text). |
| **Option 2** | Proper relational design with foreign keys ensures referential integrity and eliminates duplication. However, it adds significant complexity to the seed script (must populate dimension tables first, then resolve FKs during transaction insert). For a 24-hour assignment with a static dataset, the integrity guarantees of normalization provide no practical benefit. The coins ledger approach also requires summing all redemptions on every balance read, which is unnecessary complexity. |
| **Option 3** | Eliminates even the coins_balance table — balance could be stored as a column on a users table. But this provides no audit trail for redemptions and makes it impossible to detect or reverse erroneous balance adjustments. | **TRADEOFFS** |
| | The flat transactions table duplicates merchant names and category names across rows rather than normalizing them — this wastes some storage (~10k rows × ~20 bytes per repeated string ≈ 200KB) but dramatically simplifies seeding and querying. The `coins_balance` as a running total means balance correctness depends on every redemption being transactional (atomic UPDATE + INSERT). If the app crashes between steps, the balance could drift — this is mitigated by wrapping in a PostgreSQL transaction block. | **NOTES** |
| | Key indexes: `idx_transactions_date`, `idx_transactions_amount`, `idx_transactions_category`, `idx_transactions_payment_status`, `idx_transactions_merchant_gin` (for text search). Seed script: `psql $DATABASE_URL -f schema.sql && python seed.py` or a single Python script using `psycopg2`. Pairs well with client-side virtualization in the table UX IPD — a single `SELECT *` returns all rows. |
