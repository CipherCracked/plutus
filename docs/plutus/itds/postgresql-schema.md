| ITD 1 - "Use a normalized transactional schema with a coins balance table for the Plutus rewards system." |  |
| :---- | :---- |
| **THE PROBLEM** | The application must serve 10,000 transactions with rich filtering (category, date, amount, payment status, merchant search) and sorting (date, amount) behind a transactions table, while also tracking per-user coin balances and redemptions for the rewards system. A single JSON dump or denormalized blob would be easy to seed but perform poorly on queries, lack proper indexing, and fail the assignment's "design an actual schema rather than dumping the JSON into a single column" requirement. | **OPTIONS CONSIDERED** |
| **Option 1** | Single `transactions` table with all fields as columns + a `coins_balance` table. Seed script loads JSON directly into the transactions table. Queries use standard SQL with indexes. | **Option 2** | Split into normalized tables: `transactions`, `categories`, `merchants`, `users`, `coins_ledger`, `rewards_catalogue`, `redemptions`. Foreign keys enforce referential integrity. |
| **Option 3** | Single `transactions` table (denormalized, flat) for the table + a separate `user_coins` table just for the rewards balance. Minimal relationships, maximal simplicity. |  |
| **REASONING** | | |
| **Option 1** | Stores all transaction fields as columns in one table (date, amount, category, merchant, payment_status, etc.). A separate `coins_balance` table tracks the current balance. This is simple to seed (one INSERT per JSON record) and fast for filtering (all columns are indexed). The `coins_balance` table stores a single running total, updated atomically on each redemption. The tradeoff: category and merchant are stored as text strings, not foreign keys, so no referential integrity on those dimensions. For a 24-hour assignment with a fixed dataset, this is acceptable — the data doesn't change. | **Option 2** | Fully normalized schema with foreign keys between transactions, categories, merchants, users, coins ledger, rewards catalogue, and redemptions. This is the "proper database design" approach. It enforces data integrity and avoids duplication. However, it requires multiple tables to seed (categories first, then merchants, then transactions with FK references), and the coins ledger would require computing the balance from a transaction log rather than storing a running total. This adds complexity to both seeding and querying that may not pay off in the assignment timeframe. |
| **Option 3** | A pragmatic middle ground: a flat `transactions` table for the table view (all columns, all indexed) and a lightweight `user_coins` integer column or small table for the balance. This is essentially Option 1 but even more minimal — perhaps a single `user_coins` table with `user_id` and `balance` columns, and redemptions logged to a `redemptions` table for audit. | | |
| **SELECTED APPROACH (tentative)** | **Option 1** — a flat `transactions` table with proper indexes + a `coins_balance` table. This satisfies "actual schema, not JSON dump" by normalizing each JSON field into a typed column, while keeping the seed script simple (one INSERT per record). The `coins_balance` table holds a single row per user with the current balance. Redemptions are logged to a `redemptions` table for audit. This can be upgraded to Option 2 later if needed. | | |
| **TRADEOFFS** | The flat transactions table duplicates merchant names and category names across rows rather than normalizing them — this wastes some storage (~10k rows × ~20 bytes per repeated string ≈ 200KB) but dramatically simplifies seeding and querying. The `coins_balance` as a running total means balance correctness depends on every redemption being transactional (atomic UPDATE + INSERT). If the app crashes between steps, the balance could drift — this is mitigated by wrapping in a transaction block. | | |
| **NOTES** | - Key indexes: `idx_transactions_date`, `idx_transactions_amount`, `idx_transactions_category`, `idx_transactions_payment_status`, `idx_transactions_merchant_gin` (for text search).<br>- The `coins_balance` table is intentionally simple (user_id, balance) rather than a ledger — computing the ledger from redemptions is possible but adds complexity.<br>- Seed script should: CREATE TABLE → INSERT categories (if normalized) → INSERT transactions → INSERT rewards catalogue → SET balance to computed default. One command: `psql $DATABASE_URL -f seed.sql` or a Python script that uses `psycopg2`.<br>- This approach pairs well with **Option 1 (client-side virtualization)** in the table UX IPD — if the frontend loads all 10k rows at once, a single SELECT * is sufficient and indexes matter less for the table itself. |
