| ITD 1 - "Use Next.js frontend + FastAPI backend + PostgreSQL, deployed via Vercel + Render + Neon with local-dev fallback" |  |
| :---- | :---- |
| **THE PROBLEM** | The assignment requires a full-stack application with specific technology constraints: React + TypeScript (Next.js preferred) for the frontend, Python (FastAPI or Flask) for the backend, and PostgreSQL (mandatory). The app must either be deployed live or accompanied by a demo video if deployment isn't possible within 24 hours. A clear decision on stack and deployment path is needed before implementation begins. | **OPTIONS CONSIDERED** |
| **Frontend: Next.js vs Vite + React** | | |
| **Option 1** | **Next.js (App Router, TypeScript)** — preferred by the assignment. Gives Server Components, API routes (can host backend in Next), file-based routing, built-in CSS support, and easy Vercel deployment. | **Option 2** | Vite + React (TypeScript) + separate CRA-style setup. More control, smaller learning curve for simple apps, but lacks Next.js benefits and is not the "preferred" stack. |
| **Backend: FastAPI vs Flask** | | |
| **Option 3** | **FastAPI** — modern, async, auto-generates OpenAPI docs, has excellent async PostgreSQL support via `databases` or `SQLAlchemy 2.0` + `asyncpg`. Type-safe with Pydantic models. | **Option 4** | Flask — mature, simple, but sync-by-default and lacks FastAPI's built-in validation and docs. |
| **Backend hosting: Render vs Railway vs Fly vs self-host** | | |
| **Option 5** | **Render** — straightforward FastAPI deployment, free tier for web services, good docs, handles PostgreSQL add-ons. | **Option 6** | Railway — similar to Render, also supports PostgreSQL. | **Option 7** | Fly.io — excellent performance but slightly more complex setup. | **Option 8** | Self-host on the dev machine + demo video — fallback if all hosted options fail within 24 hours. |
| **Database hosting: Neon vs Supabase vs Railway Postgres** | | |
| **Option 9** | **Neon** — serverless PostgreSQL, free tier sufficient for a demo, scales well, integrates with Render/Fly. | **Option 10** | Supabase — also has a free Postgres tier. | **Option 11** | Railway Postgres — bundled with backend hosting. |
| **REASONING** | | |
| **Frontend** | Next.js is explicitly "preferred" by the assignment and is the natural choice for React + TypeScript. The App Router (Next.js 13+) gives us Server Components for data fetching, which keeps the 10k-row table data out of client bundle. File-based API routes also give us the option to host the backend in Next.js as a fallback (though the assignment wants a Python backend). | | |
| **Backend** | FastAPI is the stronger choice: Pydantic models give us automatic request validation (critical for the redeem endpoint), async support handles concurrent table queries, and auto-generated OpenAPI docs make the API self-documenting. Flask would work but lacks these conveniences. | | |
| **Deployment** | The most pragmatic 24-hour path: **Vercel (frontend) + Render (backend) + Neon (PostgreSQL)**. All three offer free tiers sufficient for a demo, have straightforward setup (git push → deploy), and the combination of Render + Neon is well-documented. If any step fails, the fallback is to run everything locally (Next dev server + FastAPI on localhost + local Postgres) and record a demo video. | | |
| **SELECTED APPROACH (tentative)** | **Stack: Next.js (frontend) + FastAPI (backend) + PostgreSQL (Neon)**. **Deployment: Vercel + Render + Neon free tiers**. **Fallback: local dev + demo video**. | | |
| **TRADEOFFS** | - Hosting everything on free tiers means potential cold starts (Neon serverless) and rate limits (Vercel Hobby, Render free). For a 24-hour assignment demo, this is acceptable. <br>- If deployment proves too flaky, the local-dev + video fallback is explicitly accepted by the assignment. <br>- Using Neon's serverless Postgres may require connection pooling (e.g., `pgBouncer` on Render) to handle concurrent connections — a known gotcha worth documenting in the README. | | |
| **NOTES** | - Seed script: a Python script (`seed.py`) using `psycopg2` or `asyncpg` that reads `transactions.json`, creates the schema, and inserts all rows. One command: `python seed.py` or `psql $DATABASE_URL -f schema.sql && python seed.py`.<br>- The frontend should fetch data from the FastAPI backend (not directly from Postgres) to keep the architecture clean and match the assignment's "real API" requirement.<br>- If time is short, consider using Next.js API routes as a proxy or even hosting the entire backend in Next.js (Node.js) — but this deviates from the "Python backend" requirement, so it's a last resort. |
