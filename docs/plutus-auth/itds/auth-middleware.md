| ITD 1 - "Use Supabase Auth JWT middleware in FastAPI with application-level user isolation for multi-user Plutus." |  |
| :---- | :---- |
| **THE PROBLEM** | The IPD (`docs/plutus-expansion/ipds/multi-user-auth.md`) requires multi-user authentication without changing the database provider (Supabase PostgreSQL, already configured in `docs/plutus/itds/postgresql-schema.md`) or rebuilding the backend framework (FastAPI, per `docs/plutus-backend/intro.md`). The desktop overlay focus-trap mechanism (`docs/overlay-accessibility/itds/focus-trap-implementation.md`) must also remain intact; auth should not break the keyboard/navigation contract. | **OPTIONS CONSIDERED (Decision in bold)** |
| **Option 1** | **Supabase Auth JWT middleware (`python-jose` / `pyjwt`) in FastAPI** — a dependency (`get_current_user`) validates the Bearer token against Supabase's JWKS endpoint. `user_profiles` table links to `users` (`plutus_user` as default). Redemptions and balance filtered by `user_id` at SQL layer (`WHERE user_id = ?`). No `SELECT ... FOR UPDATE` row locks needed (single-user per account, per `docs/plutus-backend/itds/atomic-redemption.md`). Frontend (`client/src/lib/api.ts`) sends `Authorization: Bearer <token>` on every request. | **REASONING** |
| **Frontend** | Option 1 aligns with the existing `client/src/lib/api.ts` architecture: native `fetch` wrapped in SWR (`docs/plutus-client/itds/api-client-architecture.md`). Adding a header is a one-line change per request, not a restructuring. The `Overlay` and `TransactionDetail` components (`docs/overlay-accessibility/`) don't interact with auth state directly; only data-fetching and mutation endpoints (`/api/redeem`, `/api/balance`) need user scoping. |
| **Backend** | FastAPI dependencies (`docs/plutus-backend/intro.md` goals: separation of routes/business logic/data access) naturally accommodate a `get_current_user` dependency. The existing `main.py` endpoints (`docs/plutus-backend/intro.md`) only need `user_id` injected; no route restructuring required. The seed script (`docs/plutus-seed-script/intro.md`) initializes `plutus_user` profile; new users create profiles via the auth flow. |
| **Database** | The `redemptions` table (`docs/plutus/itds/postgresql-schema.md`) currently references `users` (`plutus_user`). Changing to reference `user_profiles` (with FK `redemptions.user_profile_id → user_profiles.id`) improves referential integrity — matching `DECISIONS.md` DT 7's observation that a flat transactions table duplicates strings, but balance/redemption tracking benefits from normalization. Application-level filtering (`WHERE user_profile_id = ?`) avoids full Supabase RLS (row-level security) complexity, which would require database policy rewrites beyond this bounded scope. |
| **Security** | JWT validation against Supabase's JWKS endpoint is standard for Supabase-hosted apps (`docs/plutus/intro.md` Assumption #8: no production-grade security required, but basic isolation is needed for multi-user). No API keys or cookie domain management (`docs/plutus-expansion/intro.md` non-goals: no production-grade security hardening). The `CORS` setting (`DECISIONS.md` #4: open `*`) remains acceptable for this demo. | **TRADEOFFS** |
|  | Adding `python-jose` / `pyjwt` to `server/requirements.txt` introduces a dependency. The `user_profiles` table adds one more table and one FK (`redemptions.user_profile_id`). The seed script must initialize both the demo user profile and handle new user profile creation. Multi-user isolation relies on application-level SQL filtering (`WHERE user_id = ?`) rather than database RLS policies — correct for this bounded scope, but requires discipline: every query that touches user-scoped data must include the filter. If a developer forgets the filter, data leaks. This is a documented risk, not a hidden one. |
| **NOTES** | - The `docs/plutus-expansion/intro.md` problem tree (`How can Plutus become less isolated?`) originates this decision; deeper sub-folders (`docs/plutus-expansion/auth/`) may handle middleware details. <br>- The `DECISIONS.md` DT 11 (two-cache ownership) remains relevant: after redemption mutation, the Zustand store and SWR cache must both receive the user-scoped balance update (`docs/plutus-expansion/ipds/multi-user-auth.md` notes this). <br>- The `docs/plutus-expansion/intro.md` assumption #5 (new feature folders for deeper decomposition) supports creating `docs/plutus-expansion/auth/` if middleware implementation grows beyond this ITD. <br>- References: `docs/plutus-expansion/intro.md`, `docs/plutus-expansion/ipds/multi-user-auth.md`, `docs/plutus/itds/postgresql-schema.md`, `DECISIONS.md` DT 7, `DECISIONS.md` DT 11, `docs/plutus-backend/intro.md`. |
