| ITD 1 - "Use Supabase Auth JWT middleware in FastAPI with direct UUID user isolation for multi-user Plutus." |  |
| :---- | :---- |
| **THE PROBLEM** | The IPD (`docs/plutus-expansion/ipds/multi-user-auth.md`) requires multi-user authentication without changing the database provider (Supabase PostgreSQL, already configured in `docs/plutus/itds/postgresql-schema.md`) or rebuilding the backend framework (FastAPI, per `docs/plutus-backend/intro.md`). The desktop overlay focus-trap mechanism (`docs/overlay-accessibility/itds/focus-trap-implementation.md`) must also remain intact; auth should not break the keyboard/navigation contract. | **OPTIONS CONSIDERED (Decision in bold)** |
| **Option 1** | **Supabase Auth JWT middleware (`supabase` Python package) in FastAPI** — a dependency (`get_current_user_id`) extracts the `sub` claim (Supabase UUID) from the JWT. The UUID is used directly as `user_id` in all tables (`transactions.user_id`, `redemptions.user_id`). No `user_profiles` mapping table. Frontend (`client/src/lib/api.ts`) sends `Authorization: Bearer <token>` on every request. | **REASONING** |
| **Frontend** | Option 1 aligns with the existing `client/src/lib/api.ts` architecture: native `fetch` wrapped in SWR (`docs/plutus-client/itds/api-client-architecture.md`). Adding a header is a one-line change per request, not a restructuring. The `Overlay` and `TransactionDetail` components (`docs/overlay-accessibility/`) don't interact with auth state directly; only data-fetching and mutation endpoints (`/api/redeem`, `/api/balance`) need user scoping. |
| **Backend** | FastAPI dependencies (`docs/plutus-backend/intro.md` goals: separation of routes/business logic/data access) naturally accommodate a `get_current_user_id` dependency. The existing `main.py` endpoints only need `user_id` (UUID string) injected; no route restructuring required. The seed script (`docs/plutus-seed-script/intro.md`) signs up the user in Supabase Auth and uses the returned UUID as `user_id` for transactions. |
| **Database** | Tables `transactions` and `redemptions` have `user_id TEXT` columns storing the Supabase UUID directly. No `user_profiles` table, no integer FKs, no mapping layer. Application-level filtering (`WHERE user_id = ?`) avoids full Supabase RLS complexity — correct for this bounded scope. |
| **Security** | JWT validation via Supabase's `auth.get_user(token)` (using the `supabase` Python package) is standard for Supabase-hosted apps. Falls back to local JWT decode without signature verification for demo resilience. No `python-jose` / `pyjwt` dependency needed. CORS setting (`DECISIONS.md` #4: open `*`) remains acceptable for this demo. | **TRADEOFFS** |
|  | No `user_profiles` table eliminates one table, one FK, and the entire mapping layer that caused the `auth_sub` mismatch bug (seed stored username string instead of UUID). Multi-user isolation relies on application-level SQL filtering (`WHERE user_id = ?`) rather than database RLS policies — correct for this bounded scope, but requires discipline: every query that touches user-scoped data must include the filter. This is a documented risk, not a hidden one. |
| **NOTES** | - The `docs/plutus-expansion/intro.md` problem tree (`How can Plutus become less isolated?`) originates this decision; deeper sub-folders (`docs/plutus-expansion/auth/`) may handle middleware details. <br>- The `DECISIONS.md` DT 11 (two-cache ownership) remains relevant: after redemption mutation, the Zustand store and SWR cache must both receive the user-scoped balance update. <br>- The `docs/plutus-expansion/intro.md` assumption #5 (new feature folders for deeper decomposition) supports creating `docs/plutus-expansion/auth/` if middleware implementation grows beyond this ITD. <br>- References: `docs/plutus-expansion/intro.md`, `docs/plutus-expansion/ipds/multi-user-auth.md`, `docs/plutus/itds/postgresql-schema.md`, `DECISIONS.md` DT 7, `DECISIONS.md` DT 11, `docs/plutus-backend/intro.md`. |
