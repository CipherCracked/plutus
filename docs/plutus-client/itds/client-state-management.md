| ITD 1 - "Use Zustand for client-side state management in the Plutus frontend." |  |
| :---- | :---- |
| **THE PROBLEM** | The Plutus client needs to share state across multiple views: the 10k-row transaction table (filters, sort, search, selected row, detail modal), the spend analytics charts (category breakdown, monthly trend, clicked segment), and the rewards redemption flow (coin balance, selected reward, redemption status). The state must be shared between sibling components and persist across navigation in the Next.js App Router. Choosing the wrong state management approach adds complexity or causes unnecessary re-renders on a 10k-row table. | **OPTIONS CONSIDERED (Decision in bold)** |
| **Option 1** | **Zustand** — a small (~1KB), hook-based state manager with no boilerplate. Create domain-specific stores (transactionStore, rewardsStore) and subscribe components individually so only interested components re-render. |
| **Option 2** | React Context + useReducer — built into React, no dependencies. But Context re-renders all consumers on any state change, which is dangerous for a 10k-row virtualized table. |
| **Option 3** | Jotai — atom-based, granular reactivity. More flexible than Zustand but adds conceptual overhead (atoms, derived atoms). |
| **Option 4** | Redux Toolkit — full-featured but heavyweight for a single-user demo. Significant boilerplate and learning curve. | **REASONING** |
| **Why Zustand** | The 10k-row table is the primary concern: when a filter changes, only the table and charts should re-render — NOT the rewards balance display, and NOT the entire row list. Zustand's `useStore` with selector functions enables fine-grained subscriptions: `useTransactionStore(state => state.filters)` re-renders only components accessing filters, not the entire store. React Context + useReducer would re-render ALL consumers on any context change, causing the virtualized table to re-render its entire visible window on every keystroke in the search box — unacceptable for 10k rows. Jotai has similar benefits but the atom abstraction adds cognitive overhead for a 24-hour assignment where team familiarity matters. Redux Toolkit is overkill — no server-state synchronization, no complex reducers, no middleware needed for a read-heavy dashboard with local mutations. |
| **Why not Context** | The classic React Context performance trap: any change to the context value triggers a re-render of ALL consumers. In the Plutus app, updating the search string or filter would re-render the rewards balance component, the header, the chart, AND the transaction table — even though only the table and chart care about those changes. For a 10k-row table, this can cause the virtualizer to re-measure rows unnecessarily. | **TRADEOFFS** |
| | | **TRADEOFFS** |
| | | - Zustand adds a dependency (~1KB) and a new concept for reviewers unfamiliar with it. The benefit (fine-grained re-renders) outweighs this cost for a 10k-row table. |
| | | - Unlike Redux, Zustand has no devtools integration out of the box (though browser extensions exist). For a 24-hour demo, this is acceptable. |
| | | - The stores are structured as small, domain-specific slices (transactions, rewards, ui) rather than a single monolithic store, making the architecture easy to reason about. | **NOTES** |
| | | - `transactionStore` holds: raw data (loaded once), filters, sort state, search query, selected transaction, detail modal state |
| | | - `rewardsStore` holds: coin balance, rewards catalogue, selected reward, redemption status |
| | | - `uiStore` holds: active view (transactions/analytics/rewards), dark mode, mobile sidebar open |
| | | - Each store is created in `src/stores/<name>.ts` with TypeScript types for full type safety |
| | | - The 10k-row data is loaded once via `useEffect` on store initialization, then stored in `transactionStore` as a plain array (virtualized rendering handles display) |
| | | - Referenced in [[api-client-architecture]] for the data-loading strategy |
