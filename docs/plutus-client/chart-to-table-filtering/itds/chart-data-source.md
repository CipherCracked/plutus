| ITD 1 - "Re-aggregate chart data from in-memory transactions for cross-filtering." |  |
| :---- | :---- |
| **THE PROBLEM** | The AnalyticsView currently fetches pre-aggregated charts from `/api/analytics` — these represent ALL transactions, not the filtered subset the user sees in the table. Clicking a chart bar does nothing because the chart and the table's Zustand store are disconnected. To enable "click a chart bar → filter the table," the charts must be computed from the same in-memory transaction array that the table filters. | **OPTIONS CONSIDERED (Decision in bold)** |
| **Option 1** | **Re-aggregate in memory using the store's `getFiltered()` transactions.** Instead of calling `/api/analytics`, compute `category_breakdown` and `monthly_trend` directly from the transactions array in AnalyticsView. When the user clicks a bar, call `setFilters({ category: [clickedCategory] })` on the store. Charts re-render from the new filtered set. |
| **Option 2** | Keep using the API endpoint but add query parameters for filtering. `/api/analytics?category=X&status=Y` returns filtered aggregates. Charts stay in sync because the API does the aggregation. |
| **Option 3** | Hybrid: fetch from API for initial load, but switch to in-memory aggregation only when filters are active. Show API-fresh data when no filters are set, switch to computed data when the user clicks a bar. | **REASONING** |
| **Why in-memory aggregation** | The 10k transactions are already loaded in the Zustand store (per the `api-client-architecture` ITD decision to load once and cache). Computing a category breakdown from 10k rows in JavaScript takes ~1-2ms — negligible. The `getFiltered()` method already exists and returns the filtered+sored array. By aggregating from this array, the charts instantly reflect whatever filters the table has active, and bar clicks propagate to the store which updates `getFiltered()` which re-renders the charts. This is a clean single-source-of-truth loop. |
| **Why not query-parameter API** | The backend FastAPI endpoint currently does a single `GROUP BY category` query. Adding dynamic filtering at the API layer would require rewriting the SQL query to support arbitrary WHERE clauses — significant backend work for a sub-problem that is purely a frontend concern. The assignment weights frontend at 72%. The in-memory approach eliminates backend round-trips entirely and keeps changes in the client. |
| **Why not hybrid** | Two code paths (API vs in-memory) means double the testing and potential for inconsistency: the API might round differently than the client, or show slightly different totals. A single source of truth (in-memory) is simpler to reason about. The API endpoint remains available as a fallback but is not the primary path. | **TRADEOFFS** |
| | | - In-memory aggregation loses any SQL-side optimization (e.g., database indexes on category). For 10k rows this is irrelevant — the array scan is sub-millisecond. |
| | | - If the dataset grows beyond ~50k rows, in-memory aggregation would need pagination. The current design accepts this limitation (documented in README). |
| | | - The summary cards (Total Spent, Coins Earned, Success Rate) must also read from `getFiltered()` instead of the full `transactions` array, so they update consistently when a bar is clicked. | **NOTES** |
| | | - `reduce`-based aggregation: `transactions.reduce((acc, t) => { acc[t.category] = (acc[t.category] || 0) + t.amount; return acc })` |
| | | - Monthly trend uses `t.timestamp.slice(0, 7)` to extract `YYYY-MM` for grouping |
| | | - Empty chart state when no transactions match filters: show "No data in current view" message |
| | | - Chart click handler: `chart.options.onClick = (e) => { const idx = e.datasetIndex, i = e.dataIndex; setFilters({ category: [data.labels[i]] }) }` |
| | | - Active filter indicator: highlight the clicked bar with `accent` color and show a "clear" button in the chart header |
