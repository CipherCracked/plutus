| ITD 3 - "Structure the FastAPI app with routes separated from DB logic using context-managed connections." |  |
| :---- | :---- |
| **THE PROBLEM** | The backend must organize code cleanly: routes, business logic, data access, and models should be separable. The assignment requires "separate routes, business logic, and data access." But it also asks for a one-command setup and runnable demo in 24 hours. The question is: how to structure a clean, production-feeling backend without over-engineering beyond the assignment's scope. | **OPTIONS CONSIDERED (Decision in bold)** |
| **Option 1** | **Single-file structure: `main.py` contains the FastAPI app, all route handlers, a context-managed `get_db()` helper, and inline data access. `models.py` contains all Pydantic models. No routers, no service layer — everything in `main.py`.** |
| **Option 2** | Multi-module structure: `app/main.py` (app creation, router inclusion), `app/routes/transactions.py`, `app/routes/rewards.py`, `app/db.py` (connection pool), `app/schemas.py` (Pydantic), `app/models.py` (ORM). |
| **Option 3** | Single file with inline SQL in route handlers, no Pydantic models — return raw dicts from `cursor.fetchall()`. |
| **Option 4** | FastAPI with SQLModel/SQLAlchemy ORM for data access, Pydantic schemas for responses, service layer for business logic. | **REASONING** |
| **Why single-file with context manager** | The assignment has exactly 5 endpoints and a single-user model. Splitting routes into separate modules would add 4+ files for negligible benefit. A single `main.py` with inline SQL keeps all the API logic visible on one screen — reviewers can understand the entire backend in one read. The `@contextmanager` function `get_db()` wraps `psycopg2.connect()` with automatic cleanup (`conn.close()` in `finally`), satisfying the "separate data access" requirement by isolating connection lifecycle from business logic. The `models.py` file keeps Pydantic models cleanly separated from route logic. This gives a clean separation: routes → `get_db()` → SQL, without the boilerplate of routers and service classes. |
| **Why not multi-module** | With 5 endpoints and 4 tables, the routing modules would be ~10 lines each. The import boilerplate (importing routers in `main.py`, exporting from each module) outweighs the organizational benefit. The assignment's 24-hour timebox favors fewer files. Multi-module structure could be a future enhancement. |
| **Why not inline dicts** | Pydantic models provide automatic OpenAPI documentation (the frontend team and reviewers can see the API spec at `/docs`), type validation on responses, and TypeScript-compatible shape documentation (the frontend's `api.ts` mirrors these models). Returning raw dicts loses all of this. |
| **Why not ORM** | SQLAlchemy adds complexity for 4 simple tables and 5 read-heavy queries. The queries are all `SELECT` statements (no complex joins or relationship loading). Writing SQL directly is clearer and more performant. ORMs are most valuable when the object graph is complex (nested relationships, lazy loading) — not the case here. | **TRADEOFFS** |
| | | - The single `main.py` file grows to ~240 lines with 5 endpoints + the `get_db()` helper. If the API grows beyond ~10 endpoints, a multi-module structure would be warranted. |
| | | - No dependency injection container — `get_db()` is a simple function called in each route. FastAPI's `Depends()` could provide DI, but adds indirection for a single connection pool. |
| | | - No separate service layer — business logic (e.g., coin computation in `compute_coins_earned`) lives in the seed script, not the API. The API endpoints are CRUD-plus (verify → deduct → log), which fits inline in route handlers. | **RESEARCH FINDINGS (psycopg + FastAPI patterns)** |
| | | Research from [Daniel Clayton (2024)](https://blog.danielclayton.co.uk/posts/database-connections-with-fastapi/) and the FastAPI discussion forums recommends: |
| | | 1. **psycopg3 (async)**: The "ultimate trio" is FastAPI + Pydantic + async `psycopg.AsyncConnection`. Async enables non-blocking I/O, which is especially valuable for the 10k-row transactions query. The context manager `async with await psycopg.AsyncConnection.connect(...) as conn:` auto-commits on success and auto-rolls-back on exception (no manual `conn.commit()` needed). |
| | | 2. **Connection pooling**: `psycopg_pool.AsyncConnectionPool` managed via FastAPI's `@lifespan` context (start on app start, close on shutdown). The article notes *"if you're building a simple FastAPI server with small load, you don't need to worry about this too much — premature optimisation is bad!"*. Our demo has 5 endpoints serving a single user — sync without pooling is acceptable. |
| | | 3. **Yield-based dependencies**: FastAPI's `yield` pattern with try/except/finally around `conn` is cleaner than manual context managers — the framework handles the commit/rollback lifecycle. |
| | | **Our choice (sync psycopg2 with `@contextmanager`)**: valid for a demo but diverges from the async+pool best practice. The `get_db()` context manager now explicitly calls `conn.commit()` on successful exit and `conn.rollback()` on exception, with `conn.close()` in `finally`. This research-driven update fixed the original gap where rollback was implicit-only (via psycopg2's connection close). The `redeem_reward` endpoint's manual `conn.commit()` was removed since `get_db()` handles it automatically — a developer can no longer accidentally double-commit. |
| | | - File structure: `server/main.py` (FastAPI app + 5 route handlers + `get_db()` context manager), `server/models.py` (9 Pydantic models matching `client/src/lib/api.ts`), `server/requirements.txt` (fastapi, uvicorn, pydantic, psycopg2-binary, python-dotenv) |
| | | - The `get_db()` function uses `psycopg2.connect(DATABASE_URL)` directly — no connection pooling. For a demo this is fine; `psycopg2.pool.SimpleConnectionPool` could be added later. Per Daniel Clayton's article, pooling is premature optimization for small load. |
| | | - CORS open to all origins (`allow_origins=["*"]`) — deliberate for this public demo API (no credentials involved); an `ALLOWED_ORIGINS` env var can restrict it to specific origins when set |
| | | - The `load_dotenv()` call at the top of `main.py` loads from both `server/.env` and `../.env` for flexible development setups |
| | | - Future enhancement: migrate to `psycopg[async]` + `httpx` (async frontend fetch) for non-blocking I/O on the 10k-row dataset query |
