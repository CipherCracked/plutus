| ITD 1 - "Expose a 5-endpoint REST API returning full-dataset JSON, not paginated or filterable." |  |
| :---- | :---- |
| **THE PROBLEM** | The Plutus frontend caches all 10k transactions in Zustand and performs filtering, sorting, and search client-side (per the `client-state-management` ITD). The API must serve the full dataset in a single call so the frontend doesn't make per-filter API requests, which would add 100ms+ latency to every search keystroke. But returning 10k rows as JSON risks high memory usage and slow first-load. The question is: what is the right contract between backend and frontend for the transactions endpoint? | **OPTIONS CONSIDERED (Decision in bold)** |
| **Option 1** | **Full-dataset GET endpoint — `/api/transactions` returns all 10k rows sorted by timestamp DESC, no query parameters.** The frontend's `useSWR('/api/transactions')` hook fetches once and caches. All filtering happens in the Zustand store's `getFiltered()` method, which operates on the cached array in <5ms. |
| **Option 2** | Paginated endpoint with `limit` and `offset` query parameters (e.g. `/api/transactions?limit=50&offset=100`). The frontend would need to fetch pages lazily as the user scrolls. |
| **Option 3** | Filterable endpoint with query parameters for category, status, date range, etc. The frontend sends filter values as URL params and the backend runs `WHERE` clauses. |
| **Option 4** | GraphQL endpoint — the frontend queries exactly the fields it needs, with built-in filtering and pagination arguments. | **REASONING** |
| **Why full-dataset** | The frontend's architecture (SWR + Zustand caching + react-virtual) was designed around a single full-load call. The `client-state-management` ITD explicitly chose this to enable instant search-as-you-type — if the API only returned pages, every keystroke would trigger a network request, and the UX of instant filtering would be impossible. The 5–8MB JSON payload loads in ~200ms over localhost, which is acceptable for a demo. The backend can add query parameters later (Option 3) without breaking the frontend, since they'd be optional. The simplicity of "return everything" matches the 24-hour assignment's emphasis on depth over breadth. |
| **Why not paginated** | react-virtual (the frontend's virtualization library) requires random access to any row index for scroll-based rendering. Pagination would require the virtualizer to wait for page fetches, breaking the scroll experience. The assignment requires "10k-row dataset handling" as a top-3 evaluation criterion — pagination would degrade this to "50 rows per page" which misses the point. |
| **Why not filterable** | Server-side filtering would require the backend to implement every filter dimension (category, status, payment_method, date range, amount range, text search) and keep them in sync with the frontend's filter UI. This doubles the filtering logic. Since the frontend already has the full dataset cached, client-side filtering is free (sub-millisecond). |
| **Why not GraphQL** | Adds a dependency (graphene or strawberry) and complexity for a 4-endpoint API. The response shapes are simple and fixed. GraphQL's query flexibility is unused when the frontend always fetches all 10k transactions. | **TRADEOFFS** |
| | | - A 5–8MB JSON response on initial load is slower than paginated delivery (first meaningful paint is delayed by the fetch). For a demo on localhost, this is ~300ms — acceptable. |
| | | - Memory: 10k Transaction objects in the browser's JavaScript heap consume ~8–12MB. Fine for modern browsers; would need pagination beyond ~50k rows. |
| | | - No server-side search index — merchant search is a JavaScript `.includes()` scan over 10k strings, which takes <2ms (sub-millisecond per 1000 rows). Negligible. |
| | | - No bandwidth optimization for mobile users — the full dataset is always downloaded regardless of what the user is viewing. Acceptable for a demo. | **NOTES** |
| | | - Endpoint signature: `GET /api/transactions` → `Transaction[]` (no query params) |
| | | - Response sorted by `timestamp DESC` so newest transactions appear first by default |
| | | - The `AnalyticsResponse` type from `/api/analytics` is defined but the frontend computes charts in-memory per the `chart-data-source` ITD |
| | | - Future enhancement: add optional `?limit=N&offset=N` params while keeping the default (no params = all rows) for backward compatibility |
| | | - Referenced in: `docs/plutus-client/itds/api-client-architecture.md` (frontend's decision to cache full dataset) |
