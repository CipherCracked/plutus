# Mutation Validation — ITDs

| ITD 2 - "Reuse seed.py normalization logic for timestamp, status, amount; validate required fields in Pydantic model; enforce type-aware field permissions; reject duplicate IDs on create." |  |
| :---- | :---- |
| **THE PROBLEM** | Transaction mutation needs validation consistent with the seed script: timestamp normalization (ISO, epoch ms, date-only, slash format), status uppercase, coin calculation (1 coin/₹100, cap 50, only SUCCESS for Type 1; 0 coins for Type 2), required fields (merchant, category, amount, timestamp, status, payment_method). **Type-aware validation**: Type 1 allows only merchant/category edits; Type 2 allows all fields. Duplicate ID handling on create. Validation must run on both frontend (immediate feedback) and backend (authority). |
| **OPTIONS CONSIDERED (Decision in bold)** | |
| **Option 1** | **Centralize validation logic in a shared module (`server/validation.py`) with pure functions. Backend uses it in Pydantic validators and endpoint logic. Frontend ports the same logic to TypeScript (`client/src/lib/validation.ts`). Reuse `normalize_timestamp`, `normalize_status`, `compute_coins_earned` from `seed.py` directly. Add `validate_type1_edit_fields(existing, updated)` and `validate_type2_edit_fields(existing, updated)` for type-aware field permissions.** | **REASONING** |
| **Backend** | Extract `normalize_timestamp`, `normalize_status`, `compute_coins_earned` from `seed.py` into `server/validation.py`. Add type-aware validation functions. `TransactionCreate` / `TransactionUpdate` Pydantic models use `@field_validator` to call these. Endpoint calls validation before insert/update. Returns 422 with field-specific errors. On PUT: fetch existing transaction, check type, validate only allowed fields changed. On DELETE: check type, 403 if Type 1. | **TRADEOFFS** |
| **Frontend** | Port the same three functions to `client/src/lib/validation.ts`. Add type-aware field permission check: `getEditableFields(transaction_type)` returns allowed field names. Form validation runs on blur/submit. Shows inline errors. Disables blocked fields for Type 1 in edit form. Optional: call `/api/transactions/validate` endpoint for server-side preview (not needed initially). | **NOTES** |
| **Duplicate ID** | On create: if client somehow sends ID (not in Option 1 API design), reject if exists. Server-generated UUIDs make this virtually impossible. | |
| **Coin calculation** | `compute_coins_earned(amount, status, transaction_type)` — single source of truth. For Type 1: 1 coin/₹100, cap 50, SUCCESS only, positive amounts. For Type 2: always 0. Backend recalculates on every create/update (Type 2 always 0, Type 1 only if amount/status changed — but those are blocked). Frontend shows preview. | |
| **Option 2** | Duplicate validation logic in Pydantic models and TypeScript separately. No shared module. | |
| **Option 3** | Only backend validates; frontend shows generic "invalid input" errors. | |
|  | Reusing `seed.py` logic ensures mutation coins match seeded transactions exactly. Centralized module avoids drift. Pydantic v2 field validators are the right place for this. Frontend port is necessary for UX — users shouldn't wait for server round-trip to see "amount required." Type-aware validation ensures Type 1 financial integrity. | |
